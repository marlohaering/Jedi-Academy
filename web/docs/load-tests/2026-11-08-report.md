# Live server load check, 2026-11-08

Commit 9021326 deployed to jka-web-ffa (fra), shared-cpu-1x, 2 GiB RAM, 32 slots, sv_fps 40.
Authenticated metrics endpoint, shell inclusion and gateway integration tests passed. Independent code review found no important issues.

## Method and results

Initially empty live server. All bots skill 5, unique stock bot names. Measured dedicated process CPU/RSS and localhost UDP status responses. Disabled frag/time limits during the test; restored afterwards. Queries originated from a separate loopback IP to reduce interference with gateway queries. Initial exploratory run with faster queries was discarded because responses could be filtered; an RCON command that prints nothing also need not return a packet.

Every sampled occupied-server status reported the expected 16 or 32 players. All 32 bots survived map changes to duel2 and ffa3. Maximum resident game-process RAM was about 174 MiB across both test runs. Gateway/browser/client asset memory is separate.

## Follow-up on mp/duel1

A separate 32-bot test on duel1 reproduced the degradation without another map change: initially about 15–18% game CPU and sub-millisecond UDP getinfo replies, then roughly 6% game CPU with about 92–94% VM CPU steal time and replies up to 1,522 ms. This independently uses getinfo instead of getstatus. Server logs also recorded multi-second Hitch warnings, including 5,681 ms on duel2 and 13,600 ms around the ffa3 transition.

The strongest explanation is exhaustion of Fly shared-CPU burst balance, rather than a map-specific failure. Fly documents a shared-vCPU baseline of 6.25%; after burst credit depletion the scheduler restricts CPU to that baseline. The observed fall to ~6% and rise in steal closely match this behavior. Host contention can also cause steal, so the precise platform cause is inferred; host-side burst-balance/throttle metrics were not queried. The guest cgroup was unlimited and its throttle counter zero, which does not exclude host-side scheduling limits.

Source: https://docs.fly.io/machines/cpu-performance

Low process CPU can therefore coexist with severe lag: it reports CPU received, not CPU denied. The HUD response-time warning remains useful in that situation. A persistent 32-player target should be evaluated with a performance CPU; no instance size or billing change was made.

## Limits and cleanup

Bots exercise game simulation, not 32 WebSocket connections, real player network traffic or browser rendering. Short tests cannot guarantee long-term smooth play. This reproduces a plausible mechanism for the reported connection-interrupted flashes but does not inspect client prediction or rendering.

Removed test bots, restored mp/duel1, fraglimit 30, timelimit 15, companion_paused 0 and bot_minplayers 0. Auto-stop restored separately after collecting measurements. Raw samples and a CPU/steal chart are saved alongside this report.
